# 設計判断の記録

## 2026-10-10 画面は Notion をやめ、M1 上の自前の Web 画面にする

- 決定：SQLite を唯一の正本にし、Hono + JSX + htmx の画面を `shinkyo serve` で常駐させて Tailscale 内だけに公開する
- Why：Notion に置くと、住所・交渉の経緯・業者の連絡先といった情報資産が第三者の管理下に入る。また判定・承認・メモが Notion 起点になり、SQLite が正本でなくなる
- 閲覧共有：ほかの人は閲覧だけで、操作は本人1人。Tailscale のノード共有で見せ、書き込みは本人の端末からだけ受け付ける。判定を人ごとに持つ必要はない

## 2026-10-10 言語は Python ではなく TypeScript + Bun

- 決定：TypeScript（strict）、Bun、zod、Hono、Biome、bun:test、bun:sqlite
- Why：元の仕様の Python は検討のうえ選んだものではなかった。常駐する Web 画面が加わると、型の付いた状態を画面とバッチの両方から安全に書き換えることが中心になり、静的型の価値が上がる
- zod の1つの定義から、設定の検証、`claude -p` の出力の検証、`--json-schema` に渡すスキーマの生成ができる
- 次点は Go（常駐の安定性と標準ライブラリの厚さ）。Bun の長時間常駐に問題が出たら、まず同じコードを Node で動かすことを試す

## 2026-10-10 公開リポジトリのまま運用する

- 決定：リポジトリは public のまま。業者の連絡先を含む config/agents.yaml は gitignore し、agents.example.yaml だけをコミットする
- テストの fixtures には合成データだけを置く。SUUMO の HTML や業者の実メールを公開すると、SUUMO の掲載内容の再配布や第三者の個人情報の公開になるため

## 2026-10-10 claude -p はサブスクのログインで呼ぶ

- 決定：`--bare` と API キーは使わず、サブスクのログインで `claude -p` を呼ぶ
- 影響：~/.claude のフックや設定が読み込まれる。作業ディレクトリを空の一時ディレクトリにして、リポジトリの CLAUDE.md などを読ませない

## 2026-10-10 SUUMO の取得と画面の実装で決めたこと

- listing_id は一覧の `bc` (SUUMO 物件コード)。同じ部屋でも業者ごとに別の bc になるので、unit_key で束ねる
- unit_key の建物名は一覧の名前を使う。詳細ページの建物名は一覧と異なることがある（例：一覧「〇〇I/〇〇II」、詳細「〇〇II」）
- 一覧の住所は町名までで丁目が無いことが多い
- 「200 なのに0件」は、一覧上部のヒット件数が0でないときだけパーサー破損とみなす。条件を絞った検索で本当に0件のときに誤報しないため
- 「掲載終了の可能性」は、部屋の全掲載が2回続けて一覧に無いときだけ付ける。別の業者の掲載が残っていれば募集中とみなす。検索が max_pages_per_search に収まらず途中で打ち切ったときは判定しない
- 通常の SUUMO のページには「captcha」という文字列が含まれないので、CAPTCHA の兆候の判定に使える
- 画面の操作権限は `tailscale serve` が付ける `Tailscale-User-Login` ヘッダーで判定し、無ければ閲覧専用にする。サーバーは 127.0.0.1 にしか bind しない
- tailscale serve は他サイトからのリクエストにも利用者ヘッダーを付けるので、CSRF は Origin で防ぐ。公開 URL の origin を profile.local.yaml の `web.allowed_origins` に書く

## 2026-10-10 物件写真は画面で見たときに取得して残す

- 決定：画像の URL だけを掲載と一緒に保存し、画面で表示されたときにサーバーが img01.suumo.com から取得して data/images/ に残す。掲載が終わっても見返せる
- Why：巡回のたびに全写真 (1掲載あたり約20枚) を取ると、1日の上限をすぐ使い切る。人が見た分だけ取るなら、手で SUUMO を見るのと同じ量で済む
- 画像サーバーの robots.txt は `/front/gazo/` だけを許可している。一覧の `data-imgs` と詳細のギャラリー (`data-src` と `alt` の説明) はすべてこの下にある
- 画像はページと別に間隔と上限 (1日1000枚) を持つ。人が見るときの取得なので取得時間帯では止めない。403・429 などはページと共通の停止として扱う (同じ回線から出るため)
- 閲覧者のブラウザから SUUMO へ直接リクエストさせない (サーバー経由で出す) ので、閲覧者の情報は SUUMO に渡らない

## 2026-10-10 取得時間帯は手動実行でだけ外せる

- 決定：`shinkyo fetch --ignore-active-hours` を手動確認用に用意する。間隔・上限・robots.txt・停止条件は外せない。launchd の plist にはこのフラグを入れない
- Why：時間帯の外でも動作確認できないと開発が止まる。一方で定期実行は自宅回線を守るために時間帯を守る

## 2026-10-10 評価 (J2) の作り

- 詳細を取得するまで評価しない。築年月・設備・条件 (定期借家など) は詳細ページにしか無いため
- Claude に選ばせる注意フラグは決まった語の enum にする。自由記述にすると長文になり、一覧で比べられない
- 通勤時間が stations.yaml に無い駅は通勤点を中立 (0.5) にする。駅を埋めれば点がつく
- claude -p は 8 部屋ずつまとめて呼ぶ。失敗しても基礎点だけで候補にし、人の判断が要ると通知する
- J2 は `shinkyo fetch` の最後に続けて走らせる (仕様 5章「J1 の直後」)

## 2026-10-10 単純な分類は Jev (System One) に任せ、文章が要るところだけ Claude を使う

- 決定：TypeSafe AI の Jev を、はい/いいえ・選択・段階評価で答えられる判断に使う。前例は ../gmail-triage (メール分類を Jev、低信頼分と要約を Claude)
- J2 の注意点 (北向き・定期借家など) は、フラグごとに noul の設問を作り、1部屋1回のリクエストでまとめて判定する。確率 0.7 以上を採る
- J2 の一行要約と ±10点の補正は文章が要るので Claude のまま。Jev が判定できた部屋は Claude のスキーマから flags を外す
- Jev が使えない・失敗したときは Claude に注意点も選ばせる (従来どおり)
- J4 のメール分類も同じ形にする：カテゴリを Jev の choice で判定し、確信度が低いものだけ Claude で再判定する。抽出 (日時・金額) と返信文は Claude
- Why：Jev は文字列を生成しないので、スキーマ違反が構造上起こらず、確率で迷いを検出できる。Claude に自由記述で選ばせると、注意点が長文になり一覧で比べられなかった
- 実測 (渋谷区の18部屋、2026-10-10)：Jev の注意点は元データと一致した (北向きは向きが北西・北東の部屋だけ、保証会社の条件が重いは初回80%の部屋だけ)
- API キーは `.env` の `TYPESAFE_API_KEY` (gitignore 済み)。Bun が起動時に読み込む

## 2026-10-10 写真の読み込みを速くする

- 問題：初回表示で一覧のサムネイル18枚に約20〜25秒、詳細の写真20枚に約25秒かかった。1枚ずつ「前のダウンロードが終わってから」1〜1.5秒あけて取っていたため。さらに Bun のサーバーの既定のアイドル時間 (10秒) を超えた要求が接続ごと切られていた
- 決定1：取得ジョブの最後に、見送り以外の部屋のカードの1枚目と間取り図だけを先回りして取得する。定期実行なので取得時間帯を守る
- 決定2：HttpClient は「開始の間隔」だけを直列に守り、ダウンロードは並行させる。画像の開始間隔は 0.2秒 (+0〜0.1秒)。ブラウザで SUUMO を見るときに数十枚を同時に読むより控えめ
- 決定3：画面のサーバーのアイドル時間を60秒にする
- 実測：一覧のサムネイルは 0.04秒 (先回り取得済み)、未取得の写真20枚は 5.0秒 (以前は約25秒)
- 一覧のカードの代表の掲載は「家賃+管理費 → 最終確認日時 → listing_id」の順で選ぶ。同額のときに画面と先回り取得で選ぶ掲載がずれないよう、最後に listing_id で決める

## 2026-10-10 写真は同じページ内で拡大する

- 決定：Bootstrap のモーダルとカルーセルで拡大し、前後の写真へ送れるようにする。サムネイルはリンクではなくボタンにする
- Why：リンクのままだと別タブが開くうえ、hx-boost がページ遷移として扱う
- hx-boost で body が差し替わっても効くよう、モーダルを開くときの位置合わせと説明の更新は document への委譲イベントで1回だけ登録する

## 2026-10-10 写真の種類は規則で決める (Jev は使わない)

- 決定：写真の説明 (alt) から、間取り図 / 室内・設備 / 建物・共用部 / その他 / 周辺環境 を規則で決める。保存はせず表示のたびに判定する
- 規則：「間取り」を含む → 間取り図。「まで◯m」で終わる → 周辺環境。説明が「その他」「その他設備」だけ → その他。外観・エントランス・ロビー・セキュリティ・共有・共用・駐車場・駐輪・ゴミ置 → 建物・共用部。残りは室内。説明が無ければファイル名の末尾 _co を間取り図とみなす
- Why：実データ 884 枚で Jev と規則の一致は 98% (868 枚)。食い違った 16 枚はすべて説明が「その他」「その他設備」だけで、Jev にも手がかりが無かった。規則なら API・キー・失敗時の分岐が要らず、結果も毎回同じになる
- 表示：間取り図は詳細ページ上部の専用枠に、切り取らず全体を常に出す。周辺環境は参考程度なので小さく出す

## 2026-10-10 一覧の絞り込み

- 条件：家賃+管理費の上限 (万円)、面積の下限、駅徒歩、築年数、間取り (複数)、最寄駅 (どれかに一致)、タグごとの あり / なし
- 条件を変えると一覧だけを差し替える (hx-select)。入力中の値と開いた条件欄を残すため
- 空の条件は送信前に取り除き、URL には指定した条件だけを残す (共有やブックマークのため)
- 間取りと駅の選択肢は、見送り以外の部屋から作る
