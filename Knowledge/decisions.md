# 設計判断の記録

## 2026-10-10 画面は Notion をやめ、M1 上の自前の Web 画面にする

- 決定：SQLite を唯一の正本にし、Hono + JSX + htmx の画面を `shinkyo serve` で常駐させて Tailscale 内だけに公開する (後に変更: Cloudflare Tunnel + Access。下の 2026-10-10 の項)
- Why：Notion に置くと、住所・交渉の経緯・業者の連絡先といった情報資産が第三者の管理下に入る。また判定・承認・メモが Notion 起点になり、SQLite が正本でなくなる
- 閲覧共有：ほかの人は閲覧だけで、操作は本人1人とした (後に変更: 権限の区別なし・人ごとの判定とメモ)

## 2026-10-10 言語は Python ではなく TypeScript + Bun

- 決定：TypeScript（strict）、Bun、zod、Hono、Biome、bun:test、bun:sqlite
- Why：元の仕様の Python は検討のうえ選んだものではなかった。常駐する Web 画面が加わると、型の付いた状態を画面とバッチの両方から安全に書き換えることが中心になり、静的型の価値が上がる
- zod の1つの定義から、設定の検証、`claude -p` の出力の検証、`--json-schema` に渡すスキーマの生成ができる
- 次点は Go（常駐の安定性と標準ライブラリの厚さ）。Bun の長時間常駐に問題が出たら、まず同じコードを Node で動かすことを試す

## 2026-10-10 公開リポジトリのまま運用する

- 決定：リポジトリは public のまま。業者の連絡先を含む config/agents.yaml は gitignore し、agents.example.yaml だけをコミットする
- テストの fixtures には合成データだけを置く。SUUMO の HTML や業者の実メールを公開すると、SUUMO の掲載内容の再配布や第三者の個人情報の公開になるため

## 2026-10-10 claude -p はサブスクのログインで呼ぶ

- 決定：`--bare` と API キーは使わず、サブスクのログインで `claude -p` を呼ぶ
- 影響：~/.claude のフックや設定が読み込まれる。作業ディレクトリを空の一時ディレクトリにして、リポジトリの CLAUDE.md などを読ませない

## 2026-10-10 SUUMO の取得と画面の実装で決めたこと

- listing_id は一覧の `bc` (SUUMO 物件コード)。同じ部屋でも業者ごとに別の bc になるので、unit_key で束ねる
- unit_key の建物名は一覧の名前を使う。詳細ページの建物名は一覧と異なることがある（例：一覧「〇〇I/〇〇II」、詳細「〇〇II」）
- 一覧の住所は町名までで丁目が無いことが多い
- 「200 なのに0件」は、一覧上部のヒット件数が0でないときだけパーサー破損とみなす。条件を絞った検索で本当に0件のときに誤報しないため
- 「掲載終了の可能性」は、部屋の全掲載が2回続けて一覧に無いときだけ付ける。別の業者の掲載が残っていれば募集中とみなす。検索が max_pages_per_search に収まらず途中で打ち切ったときは判定しない
- 通常の SUUMO のページには「captcha」という文字列が含まれないので、CAPTCHA の兆候の判定に使える
- サーバーは 127.0.0.1 にしか bind しない (権限の判定は後に廃止)
- CSRF は Origin で防ぐ。公開 URL の origin を profile.local.yaml の `web.allowed_origins` に書く

## 2026-10-10 物件写真は画面で見たときに取得して残す

- 決定：画像の URL だけを掲載と一緒に保存し、画面で表示されたときにサーバーが img01.suumo.com から取得して data/images/ に残す。掲載が終わっても見返せる
- Why：巡回のたびに全写真 (1掲載あたり約20枚) を取ると、1日の上限をすぐ使い切る。人が見た分だけ取るなら、手で SUUMO を見るのと同じ量で済む
- 画像サーバーの robots.txt は `/front/gazo/` だけを許可している。一覧の `data-imgs` と詳細のギャラリー (`data-src` と `alt` の説明) はすべてこの下にある
- 画像はページと別に間隔と上限 (1日5000枚。当初の1000枚は初日の確認と先回り取得だけで使い切ったため上げた) を持つ。人が見るときの取得なので取得時間帯では止めない。403・429 などはページと共通の停止として扱う (同じ回線から出るため)
- 閲覧者のブラウザから SUUMO へ直接リクエストさせない (サーバー経由で出す) ので、閲覧者の情報は SUUMO に渡らない

## 2026-10-10 取得時間帯は手動実行でだけ外せる

- 決定：`shinkyo fetch --ignore-active-hours` を手動確認用に用意する。間隔・上限・robots.txt・停止条件は外せない。launchd の plist にはこのフラグを入れない
- Why：時間帯の外でも動作確認できないと開発が止まる。一方で定期実行は自宅回線を守るために時間帯を守る

## 2026-10-10 評価 (J2) の作り

- 詳細を取得するまで評価しない。築年月・設備・条件 (定期借家など) は詳細ページにしか無いため
- Claude に選ばせる注意フラグは決まった語の enum にする。自由記述にすると長文になり、一覧で比べられない
- 通勤時間が stations.yaml に無い駅は通勤点を中立 (0.5) にする。駅を埋めれば点がつく
- claude -p は 8 部屋ずつまとめて呼ぶ。失敗しても基礎点だけで候補にし、人の判断が要ると通知する
- J2 は `shinkyo fetch` の最後に続けて走らせる (仕様 5章「J1 の直後」)

## 2026-10-10 単純な分類は Jev (System One) に任せ、文章が要るところだけ Claude を使う

- 決定：TypeSafe AI の Jev を、はい/いいえ・選択・段階評価で答えられる判断に使う。前例は ../gmail-triage (メール分類を Jev、低信頼分と要約を Claude)
- J2 の注意点 (北向き・定期借家など) は、フラグごとに noul の設問を作り、1部屋1回のリクエストでまとめて判定する。確率 0.7 以上を採る
- J2 の一行要約と ±10点の補正は文章が要るので Claude のまま。Jev が判定できた部屋は Claude のスキーマから flags を外す
- Jev が使えない・失敗したときは Claude に注意点も選ばせる (従来どおり)
- J4 のメール分類も同じ形にする：カテゴリを Jev の choice で判定し、確信度が低いものだけ Claude で再判定する。抽出 (日時・金額) と返信文は Claude
- Why：Jev は文字列を生成しないので、スキーマ違反が構造上起こらず、確率で迷いを検出できる。Claude に自由記述で選ばせると、注意点が長文になり一覧で比べられなかった
- 実測 (渋谷区の18部屋、2026-10-10)：Jev の注意点は元データと一致した (北向きは向きが北西・北東の部屋だけ、保証会社の条件が重いは初回80%の部屋だけ)
- API キーは `.env` の `TYPESAFE_API_KEY` (gitignore 済み)。Bun が起動時に読み込む

## 2026-10-10 写真の読み込みを速くする

- 問題：初回表示で一覧のサムネイル18枚に約20〜25秒、詳細の写真20枚に約25秒かかった。1枚ずつ「前のダウンロードが終わってから」1〜1.5秒あけて取っていたため。さらに Bun のサーバーの既定のアイドル時間 (10秒) を超えた要求が接続ごと切られていた
- 決定1：取得ジョブの最後に、見送り以外の部屋のカードの1枚目と間取り図だけを先回りして取得する。定期実行なので取得時間帯を守る
- 決定2：HttpClient は「開始の間隔」だけを直列に守り、ダウンロードは並行させる。画像の開始間隔は 0.2秒 (+0〜0.1秒)。ブラウザで SUUMO を見るときに数十枚を同時に読むより控えめ
- 決定3：画面のサーバーのアイドル時間を60秒にする
- 実測：一覧のサムネイルは 0.04秒 (先回り取得済み)、未取得の写真20枚は 5.0秒 (以前は約25秒)
- 一覧のカードの代表の掲載は「家賃+管理費 → 最終確認日時 → listing_id」の順で選ぶ。同額のときに画面と先回り取得で選ぶ掲載がずれないよう、最後に listing_id で決める

## 2026-10-10 写真は同じページ内で拡大する

- 決定：Bootstrap のモーダルとカルーセルで拡大し、前後の写真へ送れるようにする。サムネイルはリンクではなくボタンにする
- Why：リンクのままだと別タブが開くうえ、hx-boost がページ遷移として扱う
- hx-boost で body が差し替わっても効くよう、モーダルを開くときの位置合わせと説明の更新は document への委譲イベントで1回だけ登録する

## 2026-10-10 写真の種類は規則で決める (Jev は使わない)

- 決定：写真の説明 (alt) から、間取り図 / 室内・設備 / 建物・共用部 / その他 / 周辺環境 を規則で決める。保存はせず表示のたびに判定する
- 規則：「間取り」を含む → 間取り図。「まで◯m」で終わる → 周辺環境。説明が「その他」「その他設備」だけ → その他。外観・エントランス・ロビー・セキュリティ・共有・共用・駐車場・駐輪・ゴミ置 → 建物・共用部。残りは室内。説明が無ければファイル名の末尾 _co を間取り図とみなす
- Why：実データ 884 枚で Jev と規則の一致は 98% (868 枚)。食い違った 16 枚はすべて説明が「その他」「その他設備」だけで、Jev にも手がかりが無かった。規則なら API・キー・失敗時の分岐が要らず、結果も毎回同じになる
- 表示：間取り図は詳細ページ上部の専用枠に、切り取らず全体を常に出す。周辺環境は参考程度なので小さく出す

## 2026-10-10 一覧の絞り込み

- 条件：家賃+管理費の上限 (万円)、面積の下限、駅徒歩、築年数、間取り (複数)、最寄駅 (どれかに一致)、タグごとの あり / なし
- 条件を変えると一覧だけを差し替える (hx-select)。入力中の値と開いた条件欄を残すため
- 空の条件は送信前に取り除き、URL には指定した条件だけを残す (共有やブックマークのため)
- 間取りと駅の選択肢は、見送り以外の部屋から作る

## 2026-10-10 画面を React Router v8 + shadcn/ui に移す

- 決定：画面を React Router の framework mode (SSR) と shadcn/ui (Base UI + Tailwind CSS v4) で作る。入口は Hono のまま残し、人の見分け・CSRF・写真の配信を Hono で行い、残りを `createRequestHandler` に渡す。バッチ・SQLite・クエリは変えない
- Why：要件の重心が UI の質に移った。拡大表示・絞り込み・選択ボタンを自前で作り続けるより、品質の保証された shadcn/ui の部品を使う方が安い。比較表・地図・内見計画などブラウザ側の操作が増える見込みもある
- 見送った案：Bootstrap (見た目が古い)、Tailwind + Basecoat (shadcn の見た目を写しただけで部品と振る舞いが足りない)、HonoX (shadcn/ui が使いにくい)、Next.js (常駐する個人用ツールには重く、Bun と bun:sqlite との組み合わせに癖がある)
- React Router は最新の v8 を使う (v7 の framework mode の後継)。v8 では loader / action の context が必ず RouterContextProvider になり、`createContext()` のキーで値を渡す
- 落とし穴1：Hono の入口はソースの app/context.ts を、画面のビルドは同梱のコピーを読むので、`createContext()` のキーが別物になる。キーを globalThis に1つだけ置いて共有する
- 落とし穴2：トンネル経由だと URL は 127.0.0.1 のまま届き、React Router が Origin ヘッダーとの不一致で action を止める。CSRF で許可した公開 URL から来たものだけ、URL を公開側に直してから渡す
- テストは HTTP 越しに行うため、`bun run test` で画面をビルドしてから bun test を走らせる

## 2026-10-10 1日のページ取得の上限を 300 にする

- 決定：policy.yaml の daily_request_cap を 150 (仕様書の初期値) から 300 に上げる
- Why：検索を足した初日は、新着の詳細だけで 100 件を超え、150 では1日で取り終わらなかった
- 定期実行の一覧は 1日約 20〜57 回なので、平常時は 300 に届かない

## 2026-10-10 SUUMO の検索 URL のパラメータ

- 間取りは md で絞れる。01 ワンルーム、02 1K、03 1DK、04 1LDK、05 2K、06 2DK、07 2LDK、08 3K、09 3DK、10 3LDK、11 4K、12 4DK、13 4LDK、14 5K以上 (一覧ページの検索フォームから読み取った値)
- 賃料の上限は ct (万円)、co=1 で管理費込みで比べる

## 2026-10-10 一覧で必須条件を外れる掲載は詳細を取らない

- 決定：間取り・家賃・面積・駅徒歩・階・築年数は一覧の時点で分かるので、これで外れる掲載は詳細ページを取らない。評価 (J2) も、詳細が無くても一覧で外れる部屋はその場で見送る。定期借家など詳細にしか無い条件は従来どおり詳細を取ってから判定する
- Why：結果の多い検索では、新着の詳細だけで1日の上限を使い切っていた

## 2026-10-10 結果の多い検索の1ページ目だけを取ると、取るたびに部屋が入れ替わる

- 観察：SUUMO の既定の並び (おすすめ順) は取得のたびに変わる。数千件ある検索の1ページ目だけを取ると、毎回別の部屋が新着として増え、掲載終了の判定もできない (結果が数千件ある検索で実測、詳細の取得待ちが 78 → 157 件に増えた)
- 対策：仕様書どおり、検索の条件を絞って結果を max_pages_per_search ページ (60 件程度) に収める。収まらない検索はログに警告を出している

## 2026-10-10 個人の条件は *.local.yaml に置き、リポジトリにも記録にも書かない

- 決定：実際の探す条件 (criteria・searches・stations) と個人情報は gitignore した config/*.local.yaml に置く。リポジトリの同名ファイルはサンプルにし、*.local.yaml があれば優先して読む
- Why：公開リポジトリのコミットと Knowledge に、探している間取りと地域を書いて push してしまった。履歴を書き換えて force push で取り除いた

## 2026-10-10 Web画面は Cloudflare Tunnel + Access で公開し、権限の区別をなくす

- 決定：画面を Cloudflare Tunnel で公開し、Cloudflare Access のメールアドレスの許可リストで入れる人を限る。人によって権限は変えず、判定・メモ・申込の承認は誰でもできる。判定とメモは人ごとに持ち、誰の操作かと変更前の値を events に残す
- Why：複数人で見て判断する。問い合わせや申込などの重要な操作は Claude Code から行うので、画面に権限の差は要らない。誰が付けた判定かが分かれば、Claude のセッションが全員の判断を踏まえて相談に乗れる
- 人の見分け方：入口で Cf-Access-Jwt-Assertion を検証 (署名・発行元・AUD) し、確認済みのメールアドレスを使う。メールアドレスのヘッダーだけでは信用しない
- 見送った案：Tailscale (閲覧する人全員にアプリが要る)、公開 URL + 自前のログイン (実装と保守が重く、直接さらされる)、ルーターのポート開放 (自宅の IP が出る)
- 問い合わせ (J3) は画面の ◎ では送らない。Claude Code で全員の判定とメモを見て決め、指示する
- 誤りの記録：公開方法を確認しないまま Tailscale を前提に実装を始めてしまい、消して提案からやり直した

## 2026-10-10 M1 へのデプロイは M1 から取りに行く (pull 型)

- 決定：M1 の launchd (`com.shinkyo.deploy`) が 2 分ごとに main を fetch し、GitHub の check-runs で CI の成功を確かめてから、版ごとのディレクトリに取り出してビルドし、`current` の symlink を差し替えて画面を再起動する。起動しなければ前の版に戻す。DB・画像・*.local.yaml・.env は shared/ に置いて各版に貼る
- Why：GitHub から M1 へ入る経路と秘密情報を増やさない。公開リポジトリなので check-runs は認証なしで読める (新しいコミットがあるときだけ呼ぶので 60 回/時に収まる)。作業ツリーに直接 pull すると、取得中のジョブが途中から別の版のファイルを読む
- 見送った案：self-hosted runner (公開リポジトリでは外部の PR が M1 上でコードを動かせる)、Actions から Tunnel 経由の SSH で押し込む (GitHub に鍵と service token を預ける)、Webhook を Tunnel で受ける (入口と署名検証が増える。遅れが問題になったら足す)

## 2026-10-10 地図と通勤時間は MapLibre + 地理院タイル、経路は NAVITIME (RapidAPI)

- 決定：地図は MapLibre GL と地理院タイル (淡色地図)。住所 → 座標は国土地理院の住所検索 API、経路は NAVITIME Route (totalnavi) を RapidAPI 経由で使う。座標と経路は住所ごとに SQLite に保存し、同じ住所と職場の組は調べ直さない。職場は profile.local.yaml の workplaces (複数可) に置き、採点・絞り込み・並べ替えは全員の時間が分かっているときの最長の時間で行う
- Why：Google の API は日本の電車の経路を返さない見込み (公式の対応表に公共交通の経路が載っていない)。地理院のタイルと住所検索はキー不要で無料。RapidAPI の料金は確かめられなかったので、1日の上限 (policy.yaml の commute) と保存で呼び出しを抑える。複数の職場は、誰か1人だけが極端に遠い部屋を避けるため最長の時間で判断する
- 注意：SUUMO の住所は町丁目までなので、座標と経路はその代表点からの目安になる。SUUMO の詳細ページには座標が無い (地図は別ページで、取得の回数を増やすので使わない)
- 実装の注意：maplibre-gl v6 は worker を別ファイル (maplibre-gl-worker.mjs) から読むので、`?url` で取り込んで setWorkerUrl に渡す。HTML のピンに transition を付けると、地図を動かすたびの transform にアニメーションがかかって追従が遅れる

## 2026-10-10 必須の設備は詳細を取ってから判定し、候補にも効かせる

- 決定：criteria の hard.required_features に挙げた名前を含む設備が詳細に無ければ見送る。一覧だけの判定では設備が分からないので見ない。条件を足したときに既存の候補からも外れるよう、評価ジョブは候補も必須条件だけ判定し直す (採点はし直さない)
